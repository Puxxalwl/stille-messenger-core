# CLIENT_RULES.md — обязательный контракт GUI-клиентов stille-messenger

Этот документ **нормативен для каждого GUI-клиента** stille-messenger
(десктоп, мобильный, веб-компаньон). Всё, что помечено ДОЛЖЕН (MUST) —
обязательно для признания клиента валидным интерфейсом stille-messenger;
СЛЕДУЕТ (SHOULD) — настоятельно рекомендуется. Проводной контракт ядра —
[`core/docs/ru/CORE-API.md`](../../core/docs/ru/CORE-API.md) (API 2.6.0);
этот файл переводит его в клиентские требования и сценарии.

Английский канон этого документа —
[`CLIENT_RULES.md`](../../CLIENT_RULES.md).

---

## 1. Подключение (MUST для всех клиентов)

- Подключение к ядру — Unix domain socket `$HOME/.stille-messenger/api.sock`
  (0700, тот же пользователь). Без TCP и HTTP.
- Протокол **бинарный, little-endian, фиксированные ширины** (без JSON и
  varint). Каждый кадр — 16-байтный заголовок + payload:

  ```
  [0..2]   магия "ZP" (0x5A50 LE)
  [2]      версия = 1
  [3]      тип: 1 запрос, 2 ответ, 3 событие
  [4..6]   метод (запрос/ответ) или id события (событие), u16 LE
  [6..10]  request_id u32 LE (ставит клиент, ядро повторяет в ответе; 0 у событий)
  [10..12] статус u16 LE (только у ответов)
  [12..16] payload_len u32 LE (макс. 16 МиБ)
  [16..]   payload
  ```

- Строки на проводе — префикс длины + сырые байты: `str16` =
  `[len u16][байты]`, `str32` = `[len u32][байты]`. Пустая строка —
  `len = 0`, без байтов.
- Первым отправить `GET_VERSION` и **отказаться работать при несовпадении
  major**. Minor/patch — предупредить. Текущая версия: `2.6.0`.
- Один `request_id` на запрос, ответы сопоставляются по нему; ответ может
  прийти в любом порядке относительно других запросов.

## 2. Bootstrap и событийная модель (MUST)

- Последовательность при подключении:
  1. `GET_VERSION` — рукопожатие возможностей.
  2. `GET_IDENTITY` — свой bundle + отпечаток.
     - Статус `NOT_INITIALIZED` (19): у ядра **нет профиля** (демон
       стартовал в режиме восстановления). Перейти к §3.
  3. `LIST_CONTACTS`, далее `GET_HISTORY` по каждому открытому чату по
     требованию.
- **Без busy-polling.** Изменения приходят кадрами-событиями (тип 3);
  клиент ДОЛЖЕН держать соединение и обрабатывать минимум:
  `MESSAGE_RECEIVED`, `MESSAGE_DELIVERED`, `PRESENCE`, `REACTION`,
  `CONTACT_JOINED`, `CONTACT_PROFILE`, `FILE_RECEIVED`, `FILE_SENT`,
  `CALL_STATE`, `CONFIG_CHANGED`. При потере сокета — реконнект и
  повторный bootstrap.
- История запрашивается один раз на чат (`GET_HISTORY`), дальше
  поддерживается событиями. Не перечитывать всю историю при каждом фокусе.

## 3. Онбординг: три пути старта (MUST поддержать все три)

Свежее устройство находится ровно в одном из состояний:

1. **Локальный профиль существует** — `GET_IDENTITY` отвечает OK. Показать
   чаты.
2. **Новый аккаунт** — пользователь хочет новую личность: клиент ДОЛЖЕН
   создать профиль через CLI ядра: `stille-messenger-core init` (пишет
   `~/.stille-messenger/zig-seed`, 0600), затем запустить `stille-messenger-core serve`.
   Демон, уже работающий в режиме восстановления, не провижнится через
   `init`; перезапустить его после `init`.
3. **Восстановление аккаунта** — пользователь восстанавливает личность из
   recovery-пакета. Сценарий — §4.

> Замечание: `init` — единственный способ создать новую личность; в API
> нет метода «создать личность» намеренно (создание личности — локальное
> разовое осознанное действие, а не удалённая операция).

## 4. Восстановление доступа (MUST)

Ядро поддерживает **восстановление без истории**: новое устройство
восстанавливает сид личности, профиль, контакты, маршруты, блокировки и
конфигурацию из шифрованного пакета. История сообщений и файлы в пакет НЕ
входят: после восстановления устройство начинает с пустой историей, но
собеседники видят того же человека (тот же bundle) и продолжают писать в
те же чаты.

### 4.1 Секрет и блоб

- Блоб запечатывает ядро (ChaCha20-Poly1305); ключ выводится
  (HKDF-SHA256) из 32-байтного **секрета разблокировки**, который
  передаёт клиент. Ядро этот секрет не хранит.
- Клиент ДОЛЖЕН получать секрет разблокировки одним из двух способов:
  1. **Passkey с расширением WebAuthn PRF** (предпочтительно). При
     регистрации (§4.2) клиент сгенерировал случайную 32-байтную
     **PRF-соль** и сохранил её в метаданных блоба. При разблокировке —
     вычислить PRF с этой солью; 32-байтный результат и есть секрет
     разблокировки.
  2. **Код восстановления** (фолбэк, ДОЛЖЕН быть предложен). Случайный
     32-байтный код, показанный пользователю ровно один раз при
     регистрации группами base32/hex и не хранимый клиентом. Пользователь
     вводит его, когда passkey недоступен (другая платформа, потерянное
     устройство).
- Блоб и PRF-соль живут в **личном облаке пользователя**. Референсный
  бэкенд: Google Drive, OAuth-scope
  `https://www.googleapis.com/auth/drive.appdata` (скрытый
  per-application `appDataFolder` — файлов не видно, квота на
  приложение). Допустимо и другое пользовательское хранилище с теми же
  свойствами. Клиенту ЗАПРЕЩЁН проектный сервер для бэкапов.

### 4.2 Регистрация (первичная настройка, после создания профиля)

1. Сгенерировать случайную 32-байтную PRF-соль; создать WebAuthn-passkey
   с возможностью `prf`:

   ```js
   const credential = await navigator.credentials.create({
     publicKey: {
       // rp, user, pubKeyCredParams, challenge как обычно (ES256/EdDSA)
       extensions: { prf: {} },          // запросить поддержку PRF
     },
   });
   ```

   Если аутентификатор не поддерживает PRF (проверить
   `credential.getClientExtensionResults()`) — фолбэк на код
   восстановления.
2. Вычислить PRF с солью — это секрет разблокировки:

   ```js
   const assertion = await navigator.credentials.get({
     publicKey: {
       challenge, allowCredentials: [{ id: credential.rawId, type: "public-key" }],
       extensions: { prf: { eval: { first: prfSalt } } },
     },
   });
   const unlockSecret = assertion.getClientExtensionResults().prf.results.first; // 32 байта
   ```

   Для кода восстановления: `crypto.getRandomValues(new Uint8Array(32))`,
   показать пользователю и использовать эти байты как секрет.
3. Вызвать ядро: `CREATE_RECOVERY_BACKUP` (41), payload
   `[unlock_secret 32]` → ответ `[backup str32]`.
4. Загрузить блоб в облако пользователя под фиксированным именем,
   например `stille-recovery-v1.bin`, вместе с маленьким сайдкаром
   публичных метаданных (PRF-соль, дата создания, версия API ядра).
   Сайдкар не секретен; блоб — да (см. §5).

### 4.3 Частота бэкапов (MUST)

- Повторять шаги 3–4 из §4.2 (CREATE + загрузка) после **изменений
  профиля**: имя/аватар, контакт принят/добавлен/удалён, блокировка и
  разблокировка, смена конфигурации ядра (server mode, релеи, Tor).
- НЕ создавать/загружать бэкап на каждое сообщение или по таймеру —
  истории в пакете нет, активность сообщений триггером не является.
- Хранить предыдущую версию блоба до успешной загрузки новой
  (атомарная замена), чтобы неудачная загрузка не уничтожила последний
  рабочий бэкап.

### 4.4 Восстановление на свежем устройстве

1. Запустить ядро: `stille-messenger-core serve`. Без файла сида демон
   стартует в **режиме восстановления** (эфемерная личность, сетевых
   потоков нет). `GET_IDENTITY` отвечает `NOT_INITIALIZED` — это сигнал
   онбординга.
2. Пользователь выбирает облачный аккаунт; клиент скачивает блоб (и
   сайдкар с PRF-солью).
3. Клиент выводит секрет разблокировки: PRF с сохранённой солью или код
   восстановления, введённый пользователем.
4. Вызвать `RESTORE_RECOVERY_BACKUP` (42), payload
   `[backup str32][unlock_secret 32]` → ответ
   `[bundle 64][fingerprint 32][name str16]`.
   - `OK`: профиль провижен; демон поднимет сеть сам. Показать
     восстановленное имя и дать сверить отпечаток (тот же UX, что при
     первом знакомстве: голос/QR).
   - `BAD_RECOVERY` (18): неверный секрет разблокировки или битый блоб.
     Предложить фолбэк (код восстановления, если пробовали PRF), затем
     повтор. Ограничить слепые повторы в UX (отказ детерминированный, не
     флейковый).
   - `ALREADY_PROVISIONED` (20): профиль на устройстве уже существует. Не
     затирать молча; предложить явный деструктивный сброс (удалить
     `~/.stille-messenger` и перезапустить демон) с подтверждением.
   - Пустой блоб → `BAD_ARGS`; это баг клиента, никогда так не слать.
5. После восстановления: обычный bootstrap (§2). История пуста; контакты,
   маршруты, блокировки и конфигурация на месте.

### 4.5 Лимиты (учесть в UX)

- Блоб ≤ 92 786 байт; контакты ≤ 256; блокировки ≤ 256; аватар ≤ 16 000
  байт; имя профиля ≤ 32 байта.
- Восстановление работает только в **пустой профиль** (маппинг статусов —
  §4.4).
- Одна пара passkey+соль на бэкап. Смена секрета = повторная регистрация
  (CREATE с новым секретом + загрузка); старый блоб становится
  нечитаемым мусором — блобы заменяются атомарно (§4.3).

## 5. Правила безопасности (MUST, все клиенты)

- **Никогда не логировать** секрет разблокировки, вывод PRF, байты кода
  восстановления, содержимое блоба. Блоб — непрозрачные байты: не
  парсить, не инспектировать, не отрисовывать.
- **Никогда не показывать и не экспортировать** `~/.stille-messenger/zig-seed`
  (сырой сид личности). Сид — это вся личность; путь восстановления
  существует именно затем, чтобы сид не приходилось переносить руками.
- Зануливать буферы секрета после использования (zero-fill; в JS —
  отбросить все ссылки на `ArrayBuffer`).
- PRF-соль — публичные метаданные; хранить рядом с блобом можно.
- Код восстановления показывается один раз при регистрации и никогда не
  сохраняется, не синхронизируется и не логируется клиентом.
- Транспорты кроме собственных ядра (UDS для ядра, OAuth для облака
  пользователя) НЕ ДОЛЖНЫ вводиться клиентом для материалов личности.
- При выходе/«стереть устройство»: удалить локальный `~/.stille-messenger` (с
  подтверждением); облачный блоб остаётся — это и есть путь
  восстановления, его удаление — отдельное явное действие пользователя.
